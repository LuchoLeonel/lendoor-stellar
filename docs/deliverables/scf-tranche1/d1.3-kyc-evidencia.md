# D1.3 — Gate de KYC en vivo: borrow bloqueado → aprobación → pasa

**Entregable (SCF #45, Tranche 1):** *"a wallet must pass identity verification
through an off-chain KYC provider before `borrow` is enabled"*
(`docs/ARCHITECTURE.md` §3; vendor genericizado a propósito en `21be5783`).
**Corrida:** 2026-10-12 · **PR del código:** [#6](https://github.com/LuchoLeonel/lendoor-stellar/pull/6) (+ review en `docs/reviews/pr6-kyc-gate.md`)

> **Cambio posterior (2026-10-19):** el gate ahora corre **solo en `POST /loan/borrow`**.
> `POST /loan/verify` ya no devuelve 403 por KYC: prepara la línea de crédito, y gatearlo
> dejaba la app sin límite que mostrar ni botón de borrow que dispare el KYC. Esta corrida
> (2026-10-12) es anterior al cambio; la corrida desde la app, con el préstamo on-chain,
> está en [`d1.3-kyc-app-evidencia.md`](./d1.3-kyc-app-evidencia.md).

## La corrida, paso a paso

Backend local (puerto 5050) con `KYC_GATE_ENABLED=true`, Postgres descartable en
Docker y la migración `AddKycFieldsToUsers20261011120000` ejecutada **en el
boot** (verificado en la tabla `migrations`). Usuario real creado por el flujo
público completo: auth Stellar SEP-53 con keypair descartable
(`GC67V4D2…Y4NIA3D`) → nonce → firma ed25519 → `/auth/stellar/verify` →
accept-terms → email OTP → workType → phone OTP. **Cero seeds por SQL.**

| Paso | Request | Respuesta real |
|---|---|---|
| (a) borrow/verify con `kycStatus='none'` | `POST /loan/verify` y `POST /loan/borrow` | **403** `"Necesitás completar la verificación de identidad (KYC) antes de operar tu línea de crédito."` |
| (b) arranca la verificación | `POST /kyc/start` | `{"status":"pending","sessionId":"fake-03073aef-…","verificationUrl":"https://kyc.invalid/fake/…"}` |
| — estado intermedio | `GET /kyc/status` | `{"status":"pending"}` (el gate sigue bloqueando) |
| (c) el vendor sandbox decide | `POST /kyc/sandbox/decision` `{"sessionId":"fake-03073aef-…","decision":"approved"}` | `{"ok":true}` HTTP 200 |
| (d) refresh del estado | `GET /kyc/status` | `{"status":"approved"}` |
| (e) reintento de borrow/verify | mismos requests que (a) | el 403 de KYC **desaparece**; ambos avanzan hasta la escritura on-chain y fallan por `Account not found: GDGW…` (operator descartable sin fondear — ver notas) |

**Estado persistido (fuente de verdad del gate):**

```
walletAddress = GC67V4D2…Y4NIA3D · kycStatus = approved · kycProvider = fake
kycSessionId = fake-03073aef-8219-4058-9f5d-ec7711750ccb
kycApprovedAt = 2026-10-12 20:35:42+00
```

## Reproducir

```bash
# 1) Infra descartable
docker run -d --name lendoor-kyc-demo-pg -e POSTGRES_PASSWORD=<random> \
  -e POSTGRES_DB=lendoor_kyc_demo -p 5433:5432 postgres:16-alpine
docker run -d --name lendoor-kyc-demo-redis -p 6379:6379 redis:7-alpine

# 2) backend/.env mínimo (gitignoreado): POSTGRES_* (localhost:5433),
#    BLOCKCHAIN_GATEWAY=soroban, STELLAR_OPERATOR_SECRET=<keypair descartable>,
#    SELF_SCOPE=lendoor-kyc-demo, BACKEND_URL=http://localhost:5050,
#    PORT=5050, KYC_GATE_ENABLED=true   # sin KYC_FAKE_AUTO_APPROVE

# 3) Schema en DB fresca (ver nota sobre migraciones) y boot
cd backend
npx ts-node --transpile-only -r tsconfig-paths/register -r dotenv/config \
  src/scripts/kyc-demo-bootstrap.ts
yarn start

# 4) Flujo: /auth/nonce → firmar SEP-53 → /auth/stellar/verify →
#    /user/accept-terms → /user/verify-email (OTP en el log "[DEV] OTP") →
#    /user/verify-otp → /user/verify-phone (+ OTP del log) →
#    /loan/verify ⇒ 403 KYC → /kyc/start → /kyc/sandbox/decision approved →
#    /kyc/status ⇒ approved → /loan/verify ⇒ ya no bloquea el KYC
```

## Notas honestas

- **El provider es el fake sandbox** (`FakeKycProvider`, binding único en
  `KycModule`): es lo comprometido para testnet; un vendor real entra por el
  MISMO puerto (`KycProviderPort`) cambiando solo el binding. Con un vendor
  real, `/kyc/sandbox/decision` devuelve 403 (guard por `instanceof`).
- **El paso (e) no termina en un préstamo:** tras pasar el gate, la escritura
  on-chain falla con `Account not found: GDGW…` porque el
  `STELLAR_OPERATOR_SECRET` local es un keypair descartable nunca fondeado (y
  tampoco es el operator autorizado del LoanManager). Es el comportamiento
  correcto: lo que el entregable mide es que el **gate de KYC** deja de
  bloquear, y eso se ve en que el error pasa de 403-KYC a un error on-chain
  posterior. En el backend vivo (operator real) este paso continúa normal.
- **Dos OTP (email y teléfono) salieron del log del backend** (`[DEV] OTP …`):
  sin SMTP/Kapso configurados el código degrada a log de dev por diseño. El
  flujo y la validación del OTP son los reales.
- **Migraciones en DB fresca:** la cadena completa asume el schema de la DB
  viva — TypeORM ordena por el sufijo numérico del NOMBRE DE CLASE y en DB
  vacía `SchemaHardening20260224000000` corre antes que las que crean
  `notifications` (sufijos `1712…`), y explota. `src/scripts/kyc-demo-bootstrap.ts`
  lo resuelve para el demo: corre las 2 migraciones base, alinea con
  `synchronize()`, dropea las columnas KYC y marca todo como aplicado MENOS
  `AddKycFieldsToUsers20261011120000` — así la migración del entregable corre
  de verdad en el boot. Esto NO afecta a la DB viva (allí el schema ya existe).
- **Fix de integración encontrado en esta corrida:** el primer boot real murió
  con `Nest can't resolve dependencies of the AccessTokenGuard` — `KycModule`
  usaba el guard sin importar `AuthModule` (la suite unitaria no lo ve porque
  instancia a mano). Corregido en `src/kyc/kyc.module.ts` igual que
  `UserModule`/`ContractModule`. Gates tras el fix: `tsc --noEmit` 0 ·
  **189/189 tests** (con `KYC_GATE_ENABLED=false`, el default; prendido, 2
  specs de loan-verification fallan a propósito — el gate bloquea, que es
  exactamente lo que el flag controla).
