## Reproducir

```bash
# env: EVM_PRIVATE_KEY, STELLAR_RELAYER_SECRET, CCTP_BENEFICIARY,
#      CCTP_MODE=vault, CCTP_VAULT_ID, CCTP_AMOUNT_USDC (ver cctp-demo.ts)
cd backend
yarn cctp:demo trustline        # una vez: trustline USDC del relayer
yarn cctp:demo burn             # approve + depositForBurnWithHook en Base Sepolia
yarn cctp:demo deliver <burnTx> # Iris → mint_and_forward → deposit_from
```

## Nota de alcance (pedida en la review de Tranche 1)

> **Scope note:** the submission brief said "bridge USDC from Celo". Celo is not
> a CCTP domain, so D1.1 bridges from **Base Sepolia** (CCTP domain 6) into the
> Stellar vault (domain 27). Reviewers accepted this on 2026-10-23. If Circle
> adds Celo, the same code runs by changing the chain config (`cctp-chains.ts`).
>
> **Retry / reconciliation:** implemented as a tested state machine
> (`cctp-transfer.ts`: `pending → attested → submitting → delivered | failed`,
> with Iris backoff on HTTP 429, retryable submits and requeue with the same
> nonce; specs in `cctp-transfer.spec.ts`, `iris-client.spec.ts`,
> `cctp-executor.spec.ts`). Today it is driven from the CLI (`yarn cctp:demo`),
> **not yet as a long-running service** with its own scheduler; that is the
> natural next step.

## Notas honestas

- **Source chain:** ver la nota de alcance de arriba. CCTP **no soporta Celo**
  como dominio (verificado contra la config oficial de Circle).
- **Standard Transfer** (finality 2000, `maxFee 0`): sin fee on-chain de
  Circle; la attestation tarda minutos. Fast (1000) exigiría `maxFee > 0`.
- Gotcha operativo: tras el `approve`, el `estimateGas` del burn puede ver
  estado viejo en el RPC público balanceado ("transfer amount exceeds
  allowance") — reintentar alcanza.
- 🔴 Testnet de Stellar se resetea el **2026-12-16**: estos contratos y txs
  mueren con el reset; los links de Basescan sobreviven.
